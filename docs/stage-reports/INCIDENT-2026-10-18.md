## 2. Hypotheses (ranked; none confirmed)

**E1-A (best supported).** Someone in VS Code ran `npm run db:bootstrap` at about 10:39, typed the PostgreSQL administrator password at psql's prompt, and the script then **stopped before writing `.env`**. For example, Ctrl+C or closing the terminal while psql showed its result table in a pager; the agent later found that psql's pager can appear to hang there and switched it off.

Supporting evidence:
- facts 3, 4, 6 and 7;
- **the transaction gap fits exactly.** Between the read-only setting (48920) and the CONNECT grant (48928), the Phase B script makes exactly 7 writes:
  - 4 password statements, each its own transaction (48921–48924);
  - REVOKE ALL FROM PUBLIC on both databases (48925);
  - CONNECT for migrator and app (48926);
  - CONNECT on `pbe_test` for the restore login (48927).
  The membership grant writes nothing (fact 2, 764). So the CONNECT grant lands on 48928.

This **corrects** STAGE-07A-BACKUP-REVIEW.md §23. That section assumed the current bootstrap file and argued it "would not have stopped" at its `\connect` step. The file in use at 10:39 had no such step.

**E1-B.** The role was created by hand, in pgAdmin (dialog or Query Tool on `postgres`) or `psql`, using the Part 1 SQL shown in this report. Fits the timing and pgAdmin's activity. Weaker: a manual sequence would normally leave a much smaller transaction gap, unless other changes happened in between.

**E2-A.** The person working in the VS Code window edited `.gitignore` and `.env` by hand at 12:07, possibly to store the administrator password for tools, and reverted both at 12:51 (Undo plus a save) after the agent reported the exposure.

**Connection between E1 and E2.** Both used VS Code under this Mac account on the same day, and both involve the administrator password. That is consistent with one person, but **not established**.

## 8. Root cause of E1 — confirmed (2026-10-18, read-only)

**What happened**, from the server log (read as administrator with the new password, secrets redacted) and file evidence:

1. **10:39:25** — `npm run db:bootstrap` was started in a VS Code terminal on this Mac and the administrator password was typed (psql process 4405). It ran the **Phase B** `bootstrap-local.sql`:
   - created `pbe_backup` and its CONNECT grants;
   - re-set the four login passwords (transactions 48915–48928);
   - small checkpoint at 10:40:53.
2. psql showed its result table in its **pager** and waited. The database session (backend **4416**, numbered in the 10:39–10:40 range) stayed open.
3. **10:47:21 and 11:09:14** — the agent edited `bootstrap-local.sql` **in place** (same file, inode 3113092), unaware that a run was paused.
4. **11:15:30** — the pager was closed. psql continued reading the file from its old end, **byte 6,565** (the size of the 103-line Phase B file, reconstructed exactly), into the edited text. That text starts mid-statement: `('pbe_restore_drill', :'restore_verifier'),`.
   - The server logged `ERROR: syntax error at or near "'pbe_restore_drill'"` (backend 4416).
   - psql stopped (`ON_ERROR_STOP`), so the script exited with an error and **did not write `.env`**.
5. **11:16:53** — `npm run db:inspect-connections` ran next, matching the VS Code terminal-history order.

**Who:** a person at this Mac account, in VS Code, who knew the administrator password. The records name no person.

**Agent contribution (disclosed):**
- The agent's in-place edits of a file being executed made that run fail at its very end, so `.env` was never updated.
- They also caused the verifiers to be logged: the Phase B file did not yet switch off error-statement logging.
- The agent did not know a run was in progress.

**Exposure from this:** server-log lines 625–626 of `postgresql-2026-10-18_100920.log` contain the SCRAM **verifiers** of `pbe_restore_drill` and `pbe_backup`.
- Both passwords are 256-bit random, so the verifiers cannot practically be reversed, and a verifier alone does not allow login.
- The log is readable only by the `postgres` system account and database administrators.
- Low risk. Both passwords are replaced when the bootstrap is next run successfully, and the backup login's password is reset at that time anyway.

**Lessons, to apply going forward:**
- Files the owner may be running (`bootstrap-local.sql`) must be replaced **atomically** (write a new file, then rename), never rewritten in place. A running psql then keeps reading the old version.
- The bootstrap now switches the pager off (`\pset pager off`, added 11:09), so a run cannot sit paused.
- Proposed (not done): have `db-bootstrap.cjs` pass psql a snapshot of the SQL taken at start.

**E2:** the `PGADMIN` value was 6 characters long, the same length as the administrator password given in chat. Consistent with someone storing the administrator password in `.env`; not proven.
