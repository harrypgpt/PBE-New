## 2. Local-first setup (target for Stage 1–2)

Current machine inspection (2026-10-13): Node.js v24.21.0 and npm are installed. **PostgreSQL client (`psql`) not found. Docker not found.**

**PostgreSQL is the only database (ADR-021).** Minimum major version: **15**, because the design depends on `security_invoker` views (§4.6). The recommended version is 17, subject to the hosting target.

Options for local PostgreSQL (OD-004):
1. **Postgres.app** (macOS app, simplest for a non-coder). *Recommended.*
2. Homebrew `postgresql@16/17`.
3. Docker Desktop + `docker compose`. This also prepares for containerised deployment, but adds a tool.

Each option installs PostgreSQL's own client tools (`psql`, `pg_dump`, `pg_restore`), which the migration, backup and drift-check scripts use. None of the options needs Python.

Local processes:
```
apps/web   → http://localhost:3000   (Next.js)
apps/api   → http://localhost:4000   (NestJS, /api/v1)
worker     → same codebase as api, started with a "worker" command
postgres   → localhost:5432 (databases: pbe_dev, pbe_test)
files      → ./.data/files (git-ignored, encrypted with dev key)
```

Owner-friendly scripts (Stage 1–2): `npm run setup`, `npm run dev`, `npm run test`, `npm run db:migrate`, `npm run db:status`, `npm run db:new <name>`, `npm run db:check`, `npm run db:revert <id>` (guarded; §4.7), `npm run db:backup`, `npm run db:restore`, `npm run verify` (runs the full stage gate locally).

## 4. Database schema changes (no Prisma Migrate)

Governing decisions: ADR-017 (forward-only in production) and ADR-021 (SQL-first; database is the source of truth; no Prisma Migrate). Open: migration runner (OD-002), data-access layer (OD-037), migration technical reviewer (OD-038).

### 4.1 Versioning
- Migrations live in `db/migrations/` as plain SQL, one change per file, named `NNNN_short_description.sql` (4-digit, zero-padded, strictly increasing; e.g., `0007_add_dissolution_profiles.sql`).
- Each forward file has a paired **revert script** `db/migrations/revert/NNNN_short_description.revert.sql`. Where a change cannot be undone without data loss (e.g., dropping a column), the revert script says so in a header comment and contains only a `RAISE EXCEPTION` guard. Rollback then uses the backup path (§4.7, option c-2).
- Every file starts with a header block: purpose, roadmap stage, author, reviewer, whether it is destructive, expected lock impact, whether it runs in a transaction, and the related ADR/OD.
- The runner records each applied migration in `schema_migrations`: `id`, filename, SHA-256 checksum, applied_at, applied_by (database role), runner version, duration, and the application release/commit.
- **Applied migrations are immutable.** If a file's checksum differs from the recorded value, the runner stops before doing anything. A correction is always a **new** migration.
- `db/schema.sql` holds the normalised `pg_dump --schema-only` output after all migrations. It is committed and regenerated by `npm run db:check`, so reviewers can see the exact resulting schema.
- RLS policies, grants, triggers, functions and views are all created in migrations. Nothing is set up manually.
- **Database roles** (`pbe_migrator`, `pbe_app`, `pbe_readonly_report`) are cluster-level objects and need privileges the migrator must not hold. They are created by a separate, reviewed, versioned bootstrap script `db/bootstrap/roles.sql`, run once per environment by an administrator. Its use is recorded in the technical trace.

### 4.2 Review (before merge)
Every migration pull request is checked against this list. The checklist is copied into the PR and every item is answered.

| # | Check |
|---|---|
| R1 | Purpose and stage stated; header block complete |
| R2 | Destructive? (DROP, type narrowing, NOT NULL on existing data, data rewrite). If yes, expand → migrate → contract is used across releases (§4.4) and the backup-based rollback is acknowledged |
| R3 | Lock impact: no long `ACCESS EXCLUSIVE` locks on large tables; indexes on populated tables use `CREATE INDEX CONCURRENTLY` in a separate non-transactional migration |
| R4 | **Every new tenant-owned table** has `tenant_id NOT NULL`, `ENABLE` + `FORCE ROW LEVEL SECURITY`, a policy with both `USING` and `WITH CHECK`, and composite foreign keys that include `tenant_id` (§4.6) |
| R5 | Grants: `pbe_app` gets only the privileges it needs. Immutable tables get no UPDATE/DELETE grants, plus a trigger |
| R6 | Views use `security_invoker = true`. Any `SECURITY DEFINER` function is justified and added to the allow-list |
| R7 | Backward compatible with the **currently deployed** application version (required for zero-downtime deploys and application rollback) |
| R8 | Revert script present and tested, or marked irreversible with justification |
| R9 | Data migrations are batched, idempotent and do not log scientific values |
| R10 | `db/schema.sql` regenerated; drift check passes; tests added (§4.5) |
| R11 | Technical reviewer (OD-038) approved; the owner approves stage-level results |

### 4.3 Applying safely
The runner (OD-002) must do the following, regardless of which option is chosen:
1. **Connect as `pbe_migrator` only.** It refuses to run as a superuser in staging/production, or as `pbe_app`.
2. **Confirm the target.** It prints database name, host and environment, and requires an explicit confirmation flag outside local/test.
3. **Pre-flight checks:**
   - all applied checksums match,
   - no gaps or out-of-order files,
   - a backup taken and **restore-verified** within the configured window exists (staging/production),
   - the application release supports the target schema version.
4. **Take a PostgreSQL advisory lock**, so only one runner can migrate at a time.
5. **Set safe session limits:** `lock_timeout` and `statement_timeout` (configurable). Migrations fail fast instead of blocking production traffic.
6. **Run each file in its own transaction** (all-or-nothing) unless the header declares `-- pbe:no-transaction` (e.g., `CREATE INDEX CONCURRENTLY`). Non-transactional files must contain a single statement.
7. **Post-checks** after the run:
   - RLS coverage check (§4.6),
   - role and privilege check,
   - schema drift check against `db/schema.sql`,
   - application `/health/ready`.
   If any check fails, the deployment stops and the rollback procedure starts (§4.7).
8. **Record everything** in `schema_migrations` and the platform technical trace.

Production order: verified backup → migrate (expand step) → deploy the new application → smoke tests → (later release) contract step.

### 4.4 Breaking changes: expand → migrate → contract
1. **Expand:** add new columns, tables or views alongside the old ones. The old application version keeps working.
2. **Migrate:** backfill data in idempotent batches. The application writes to both old and new structures where needed.
3. **Switch:** release the application that reads the new structure.
4. **Contract:** remove the old structures in a **later** release, only after the switch has been verified in production and a fresh verified backup exists.

### 4.5 Testing schema changes
These run automatically in CI and in `npm run verify` against a real PostgreSQL instance of the target major version. No SQLite or emulators.

| ID | Test | Passes when |
|---|---|---|
| M1 | Fresh apply | All migrations apply to an empty database without error |
| M2 | Upgrade apply | Starting from the previous release's schema plus fixture data, new migrations apply and the fixture data is still valid |
| M3 | Re-run is a no-op | Running the runner twice changes nothing |
| M4 | Checksum tamper | Modifying an applied file makes the runner refuse to start |
| M5 | Revert round-trip | For each reversible migration: apply → revert → `pg_dump --schema-only` equals the pre-apply schema |
| M6 | Drift | The live schema after M1 equals the committed `db/schema.sql` |
| M7 | RLS coverage | Catalogue test (§4.6, T-ISO-01) passes |
| M8 | Role privileges | `pbe_app` is not superuser, has no `BYPASSRLS`, owns no tables, cannot run DDL |
| M9 | Immutability triggers | UPDATE/DELETE on frozen/immutable tables fails as `pbe_app` |
| M10 | Tenant-isolation suite | The full database-level and API-level isolation suite passes on the migrated schema ([TESTING_AND_ACCEPTANCE_GATES.md](TESTING_AND_ACCEPTANCE_GATES.md) §5) |
| M11 | Backup → restore | Restoring a backup taken after migration into a scratch DB passes integrity checks (§5) |

### 4.6 Database-level tenant isolation (preserved)
- RLS remains the database-level isolation control (ADR-004).
- **Foreign keys bypass RLS** when PostgreSQL checks them. So every reference between tenant-owned tables uses a **composite foreign key** `(tenant_id, parent_id) → parent(tenant_id, id)`, backed by a unique constraint on `(tenant_id, id)`. A row can then never point at another tenant's row.
- **Views** must be created `WITH (security_invoker = true)` (PostgreSQL ≥ 15). Otherwise a view runs with its owner's rights and can bypass RLS.
- **`SECURITY DEFINER` functions** are forbidden unless listed in a reviewed allow-list. A catalogue test enforces this.
- Tenant context is set with `SET LOCAL app.tenant_id` (or `set_config(..., true)`) inside each transaction, so it cannot leak to the next user of a pooled connection.
- The automated tests that prove this are listed in [TESTING_AND_ACCEPTANCE_GATES.md](TESTING_AND_ACCEPTANCE_GATES.md) §5 (T-ISO-01 to T-ISO-14).

### 4.7 Recovery and rollback
Pick the **least destructive** option that resolves the problem. Every use is recorded in the technical trace and, where tenant data is affected, in the tenant audit trail.

| Situation | Option | How |
|---|---|---|
| A migration fails part-way | **(a) Automatic transaction rollback** | The failing file's transaction is rolled back by PostgreSQL. Nothing partial remains, except in `no-transaction` files, whose single statement either completes or fails. Fix by adding a new migration; the failed one stays unapplied |
| A migration succeeded, but the new application release misbehaves | **(b) Application rollback** | Redeploy the previous application version. This works because of review item R7, which requires migrations to be backward compatible |
| The schema change itself must be undone and is reversible | **(c-1) Revert script** | The tested paired revert script is run by `npm run db:revert <id>`. It needs an explicit confirmation, a verified recent backup, and a written reason. It applies in a transaction and records a revert entry in `schema_migrations` |
| Data was lost or corrupted, or the change is irreversible | **(c-2) Restore** | Restore the pre-migration verified backup, or use point-in-time recovery in cloud, into a new database. Verify it with the §5 integrity checks, then switch over. Changes made after the backup point are lost unless point-in-time recovery covers them, so this decision needs owner approval |
| Defect found later | **(d) Forward fix** | A new reviewed migration. This is the normal production path (ADR-017) |

**Not allowed:** editing or deleting applied migration files; hand-editing production schemas outside the runner; running revert scripts automatically in a deployment pipeline.

### 4.8 Tools used by this process
- **Database tools:** PostgreSQL and its client tools (`psql`, `pg_dump`, `pg_restore`).
- **Node.js tools:** the PostgreSQL driver `pg` (pure JavaScript) and the migration runner (OD-002).
- **Not used:** Python, JVM, Perl or ORM schema generators (ADR-021, ADR-022).

## 5. Backup and restoration

| Item | Approach |
|---|---|
| Database | Local: `pg_dump` (custom format) via script. Cloud: managed automated backups + point-in-time recovery |
| Files | Object storage versioning + cross-region replication where residency permits |
| Keys | KMS-managed. Backup of key material per KMS provider guidance; **file backups without keys are unreadable by design** |
| Verification | Scripted restore into a scratch database + integrity checks: row counts, audit hash-chain verification, sample run reproduction |
| Frequency / retention | Set before production (OD-014, OD-015) |

**Rule:** a backup counts as "working" only after a restore has been executed and verified.

## 6. Future SaaS deployment (target architecture)

```
 Users ──TLS──▶ CDN/WAF ──▶ Web (Next.js) ──▶ API (NestJS, ≥2 instances) ──▶ Managed PostgreSQL (private network)
                                             │
                                             ├──▶ Worker (NestJS worker mode)
                                             ├──▶ Object storage (encrypted, private)
                                             ├──▶ KMS / Secret manager
                                             └──▶ Logs/metrics (no scientific content)
```

- Containers (one image for api/worker, one for web) on a managed container platform. **No Kubernetes requirement.** Images contain Node.js and PostgreSQL client tools only, with no Python runtime (ADR-022).
- Private networking for the database. No public database endpoint.
- **Regional data residency:** one deployment "cell" per region (e.g., EU, US, India), each with its own database, storage and keys. A tenant is pinned to one cell. The global layer holds only routing/directory data (OD-015).
- When moving to multiple API instances, rate limiting and session storage stay in PostgreSQL, not Redis, unless load testing shows a need (documented ADR required).

## 7. Cloud portability

- Use only standard PostgreSQL features (RLS, triggers, jsonb, security-invoker views). No proprietary database extensions in the core. Managed PostgreSQL services must support major version ≥ 15 and allow non-superuser migrator/app roles.
- S3-compatible storage interface and a KMS interface behind adapters.
- Containerised build. Infrastructure-as-code chosen with the hosting provider.

## 8. Release process (from Stage 1)

1. Feature branch → automated gate (`npm run verify`) → review → merge.
2. Version tag (semver), with changelog.
3. Build artifacts record the commit hash, which is embedded in runs (SCIENTIFIC §6).
4. Deploy to staging → smoke + e2e → owner approval → production.

Version control is **not yet initialised** in this workspace (OD-023).
